[Introduction]:

# Introduction

The **CANsub.4** is a compact and professional CAN bus interface with four galvanically isolated CAN buses.
It combines high performance with features matching or exceeding those typically only found in larger, more expensive devices.

The device connects via either USB<sup>[1](#usb)</sup> or Ethernet, both exposing an identical network interface<sup>[2](#net)</sup>.

The device has an [LCD color display](https://canlogger.csselectronics.com/cansub-docs/cansub4/hardware/display.html.md#display) providing useful information, such as CAN bus state, frame rate, and bus load.

A built-in web-based user interface (*webCAN*) can be accessed through a browser without installing any software<sup>[3](#tls)</sup>. The *webCAN* tool comes with a rich set of features, such as raw-frame view, decoded-frame view, and live plotting.

[python-can](https://python-can.readthedocs.io/) support is provided through the [python-can-cansub](https://pypi.org/project/python-can-cansub/) package.

The CANsub.4 has an open [API](https://canlogger.csselectronics.com/cansub-docs/cansub4/api/index.html.md#api) based on easily accessible technologies to encourage users to create 3rd-party integrations<sup>[4](#rd)</sup>.

![image](cansub4.jpg)

---
* <a id='usb'>**[1]**</a> Network over USB using the USB CDC-NCM device class.
* <a id='net'>**[2]**</a> Switching between USB and Ethernet requires only a URL change.
* <a id='tls'>**[3]**</a> The CANsub root certificate can optionally be installed in the browser.
* <a id='rd'>**[4]**</a> A range of 3rd-party integrations and code examples are available on [csselectronics.com](https://csselectronics.com/).

# Glossary

The terms below are explained as they apply to the CANsub.4.

<a id="term-API"></a>

API
: The open interface through which software controls the device. It consists of the [REST API](#term-REST-API) and the [WebSocket](#term-WebSocket) API.

<a id="term-API-version"></a>

API version
: The version number of the [API](#term-API).

<a id="term-Bit-rate"></a>

Bit rate
: The speed of the CAN bus in bits per second. Classical CAN uses one bit rate for the whole frame. CAN FD uses a [nominal bit rate](#term-Nominal-bit-rate) and a [data bit rate](#term-Data-bit-rate).

<a id="term-Bit-timing"></a>

Bit timing
: The channel settings that define the [bit rate](#term-Bit-rate) and the [sample point](#term-Sample-point).

<a id="term-Bus-load"></a>

Bus load
: The percentage of time the CAN bus is not idle. 100 percent means the bus is never idle.

<a id="term-Bus-off"></a>

Bus off
: A CAN node state entered after too many errors. The node no longer takes part in the bus traffic.

<a id="term-Byte-stuffing"></a>

Byte-stuffing
: A method for marking where one message ends and the next begins in a stream of bytes. One byte value is reserved as the boundary marker, and any occurrence of that value inside a message is replaced by a two-byte escape sequence, so the marker never appears in the message content.

<a id="term-CAN-bus"></a>

CAN bus
: A physical CAN bus network. The device can be connected to one bus per channel.

<a id="term-CAN-channel"></a>

CAN channel
: One of the numbered CAN interfaces of the device. Each CAN channel can be connected to one [CAN bus](#term-CAN-bus).

<a id="term-CDC-NCM"></a>

CDC-NCM
: The USB device class making the device appear as a network adapter.

<a id="term-Client"></a>

Client
: The software connecting to the device via the network, for example the browser running webCAN or a user script.

<a id="term-Data-bit-rate"></a>

Data bit rate
: The [bit rate](#term-Bit-rate) used for the data phase of CAN FD frames with the bit rate switch (BRS) flag set.

<a id="term-Device"></a>

Device
: The CANsub.4 CAN bus interface described by this manual.

<a id="term-Device-clock"></a>

Device clock
: The physical clock inside the device.

<a id="term-Device-ID"></a>

Device ID
: A globally unique 8-digit hexadecimal identifier of a device.

<a id="term-Device-time"></a>

Device time
: The date and time derived from the [device clock](#term-Device-clock).

<a id="term-Drift"></a>

Drift
: The gradual divergence of a clock from another clock.

<a id="term-Endpoint"></a>

Endpoint
: A single address in the REST API, such as `/api/time`, that a client reads or writes.

<a id="term-Error-active"></a>

Error active
: A CAN node state. The normal operating state, in which the node takes full part in the bus traffic.

<a id="term-Error-frame"></a>

Error frame
: A CAN bus error event.

<a id="term-Error-passive"></a>

Error passive
: A CAN node state entered after repeated errors. The node still takes part in the bus traffic, but with reduced ability to signal errors.

<a id="term-Ethernet-mode"></a>

Ethernet mode
: The operating mode in which the device transfers data via the Ethernet connection.

<a id="term-Frame"></a>

Frame
: A single CAN frame.

<a id="term-Hardware-filter"></a>

Hardware filter
: A CAN frame identifier filter applied on the device itself (in contrast to a software filter implemented by the [Client](#term-Client)).

<a id="term-HDLC"></a>

HDLC
: A communication protocol used for transmitting data between devices.

<a id="term-Hostname"></a>

Hostname
: A name assigned to a device connected to a computer network, optionally used instead of its IP address.

<a id="term-mDNS"></a>

mDNS
: A mechanism that lets a PC find a device by its hostname on a local network.

<a id="term-mTLS"></a>

mTLS
: TLS Mutual Authentication is a client authentication mechanism comparable to password protection.

<a id="term-Nominal-bit-rate"></a>

Nominal bit rate
: The [bit rate](#term-Bit-rate) used for all of a frame except the data phase of CAN FD frames with the bit rate switch (BRS) flag set.

<a id="term-NTP"></a>

NTP
: Network Time Protocol. A mechanism for keeping clocks synchronized with millisecond accuracy.

<a id="term-Offset"></a>

Offset
: - PTP: How far the device clock is from the PTP master.

<a id="term-OpenAPI"></a>

OpenAPI
: A machine-readable description of a REST API that can be used for documentation or code generation.

<a id="term-PoE"></a>

PoE
: Power over Ethernet. Providing power to a device through an Ethernet cable.

<a id="term-Power-cycle"></a>

Power cycle
: Switching the device off and on again by removing and restoring power.

<a id="term-ppb"></a>

ppb
: Parts per billion.

<a id="term-ppm"></a>

ppm
: Parts per million.

<a id="term-PTP"></a>

PTP
: Precision Time Protocol. A mechanism for keeping clocks synchronized with microsecond accuracy.

<a id="term-PTP-client"></a>

PTP client
: A network node that obtains its time from a [PTP master](#term-PTP-master) using [PTP](#term-PTP). The device is a PTP client.

<a id="term-PTP-master"></a>

PTP master
: A network node that provides time to PTP clients using [PTP](#term-PTP).

<a id="term-python-can-cansub"></a>

python-can-cansub
: A [Python package](https://github.com/CSS-Electronics/python-can-cansub) that implements the [python-can](https://python-can.readthedocs.io/) interface on top of the device [API](#term-API).

<a id="term-REST-API"></a>

REST API
: An interface using standard HTTP requests. The part of the device [API](#term-API) used for configuration and status.

<a id="term-Sample-point"></a>

Sample point
: The position in percent within a bit at which the bus level is read. Defined through the [bit timing](#term-Bit-timing).

<a id="term-Silent-mode"></a>

Silent mode
: A CAN bus mode where a node only listens and never transmits. Also called *listen-only* mode.

<a id="term-Timestamp"></a>

Timestamp
: The [device time](#term-Device-time) at which a CAN frame was on the bus.

<a id="term-TLS"></a>

TLS

<a id="term-Transmission-acknowledgement"></a>

Transmission acknowledgement

<a id="term-Transmission-sequence"></a>

Transmission sequence

<a id="term-USB-mode"></a>

USB mode

<a id="term-VPN"></a>

VPN

<a id="term-webCAN"></a>

webCAN

<a id="term-WebSocket"></a>

WebSocket

[Specification]:

# Specification

## USB

* USB-C connector
* Powered through USB connector (5 V)
* USB CDC-NCM device class

## Ethernet

* RJ45 connector
* 10BASE-T/100BASE-TX IEEE 802.3 Ethernet transceiver
* Link status LED

## Display

* 0.96” backlit LCD color display

## Network

* Network over USB (CDC-NCM) or Ethernet
* Discovery via mDNS
* Data secured using TLS
* Optional user authentication using TLS Mutual Authentication (mTLS)

## Time

* One microsecond (1 us) hardware timestamping of CAN bus frames (both RX and TX)
* Time synchronization via PTP (IEEE 1588) with a relative error approaching the timestamp resolution<sup>[1](#fn-ptp-setup)</sup>

## CAN bus

* Physical
  > * Four galvanically isolated<sup>[2](#fn-basic-isolation)</sup> physical CAN bus interfaces
  > * DB25 (D-sub25) connector
* Transceiver
  > * Compliant with ISO 11898-2:2016 (classical CAN and CAN FD)
  > * Short-circuit, bus-fault, and undervoltage protection
  > * Ideal passive behavior when unpowered (high impedance / no load)
  > * TXD dominant timeout (prevents network blocking in the event of a failure)
* Controller
  > * Based on MCAN IP from Bosch
  > * Customizable bit rate / bit timing / sample point
  > * Customizable hardware filters (range or mask)
  > * Support for bus-error monitoring
  > * Support for listen-only mode (transmission disabled)
* Application
  > * Frame rate, frame count, and bus load calculated by the device
  > * Hardware transmission jobs for high-accuracy frame spacing
  > * Frame transmission acknowledgements with actual transmission timestamps

## Mechanical

* Robust aluminum enclosure
* Flanges for secure mounting
* Dimensions: 67 x 87 x 20 mm (L x W x H)
* Operating temperature: -25 °C to +70 °C

---
* <a id='fn-ptp-setup'>**[1]**</a> The achievable relative timestamp error depends on the PTP master and network setup.
* <a id='fn-basic-isolation'>**[2]**</a> The CANsub.4 implements a *basic* galvanic isolation, making it easy to connect CAN bus networks not subjected to high voltage differences.

# Connectivity

The CANsub.4 is always powered via the USB cable. Data is transferred via either the USB cable or the Ethernet cable. In both cases, data is transferred through a network interface. The webCAN tool and the device [API](https://canlogger.csselectronics.com/cansub-docs/cansub4/api/index.html.md#api) work identically via both connections.

This section documents the data interface (USB/Ethernet), device hostname, device discovery (using mDNS), and security (using TLS).

---

[Data interface]:

# Data interface

The device selects which data interface to use based on the following logic<sup>[1](#fn-change-mode)</sup>:

```mermaid
flowchart LR

    pwr("Power on (via USB)") --> detect{Detect interface}

    detect -->|"USB host detected" | usb("USB mode<br>(data over USB)")
    detect -->|"Ethernet detected" | eth("Ethernet mode<br>(data over Ethernet)")
```

The detection state is shown on the device display, see [Connection layout](https://canlogger.csselectronics.com/cansub-docs/cansub4/hardware/display.html.md#connection-layout).

#### NOTE
The device uses distinct hostnames for the USB (`[DEVICE-ID]-usb.local`) and Ethernet (`[DEVICE-ID]-eth.local`) interfaces to prevent hostname resolution conflicts when switching between the two.

---

## USB mode

In *USB mode* the device is powered via USB and transfers data via USB.

```mermaid
flowchart LR
   USB[USB host] ===|"USB power<br>USB data" | DEV[Device]
```

When transferring data over USB, the device uses the USB CDC-NCM class<sup>[3](#fn-cdc-ncm)</sup> to expose a network interface. In this mode, the device runs a DHCP server that assigns an IP address to the connected USB host.

| Hostname          | DHCP   | Network       | Device IPv4   | Host IPv4    |
|-------------------|--------|---------------|---------------|--------------|
| `[DEVICE-ID]-usb` | Server | `10.x.y.0/24` | `10.x.y.1`    | `10.x.y.100` |

The device hostname and IP address are shown on the device display, see [Network layout](https://canlogger.csselectronics.com/cansub-docs/cansub4/hardware/display.html.md#network-layout).

The webpage hosted by the device can be accessed via:

- `https://[DEVICE-ID]-usb.local`<sup>[2](#fn-local)</sup> (e.g. `https://aabbccdd-usb.local`)
- `https://[DEVICE-IP]` (e.g. `https://10.121.15.1`)

The CANsub.4 is identified on the USB bus by the following vendor and product IDs:

| Parameter        | Value    |
|------------------|----------|
| Vendor ID (VID)  | `0x04D8` |
| Product ID (PID) | `0xE487` |

The device variant, hardware version, firmware version, and ID are stored in the USB descriptors.

Using `lsusb` to read the `iProduct` (variant, hw-ver, fw-ver) and `iSerial` (device ID) USB descriptor fields.

```console
$ lsusb -v -d 04d8:e487 | grep -e "iProduct" -e "iSerial"
  iProduct                2 CANsub.4 01.02 01.02.03
  iSerial                 3 aabbccdd
```

```mermaid
flowchart LR
   USB[USB charger] ===|"USB power" | DEV[Device]
   NET[Network] ===|"Ethernet data" | DEV
```

| Hostname          | DHCP   | Device IPv4   |
|-------------------|--------|---------------|
| `[DEVICE-ID]-eth` | Client | Assigned      |

The device hostname and IP address are shown on the device display, see [Network layout](https://canlogger.csselectronics.com/cansub-docs/cansub4/hardware/display.html.md#network-layout).

- `https://[DEVICE-ID]-eth.local`<sup>[2](#fn-local)</sup> (e.g. `https://aabbccdd-eth.local`)
- `https://[DEVICE-IP]` (e.g. `https://192.168.1.100`)

[Discovery]:

# Discovery

#### NOTE
The device ID is printed on the device enclosure and can be used to construct the device hostname as explained in [Data interface](https://canlogger.csselectronics.com/cansub-docs/cansub4/connection/data_interface.html.md#data-interface) and [Getting started](https://canlogger.csselectronics.com/cansub-docs/cansub4/getting_started/index.html.md#getting-started). This section explains how to detect a CANsub device when the device ID is unknown.

The CANsub.4 advertises itself on the local network (USB or Ethernet) using mDNS<sup>[1](#fn-mdns)</sup> and DNS-SD<sup>[2](#fn-dnssd)</sup>. This allows the device to be discovered without knowing its IP address in advance.

The device registers a service of type `_cansub._tcp` with the following properties:

| Property        | Value                                                                       |
|-----------------|-----------------------------------------------------------------------------|
| Service type    | `_cansub._tcp`                                                              |
| Hostname        | `[HOSTNAME].local`<br/>(`[DEVICE-ID]-usb.local` or `[DEVICE-ID]-eth.local`) |
| Port            | `443`                                                                       |
| TXT: `api`      | REST API version (e.g. `02.00`)                                             |
| TXT: `channels` | Number of CAN bus channels (`1`, `2`, or `4`)                               |

### Windows

On Windows, the `dns-sd`<sup>[3](#fn-dnssd-win)</sup> tool can be used for mDNS discovery.

The `dns-sd` tool used to detect a CANsub device with hostname `aabbccdd-usb`.

```doscon
C:\>dns-sd -Z _cansub._tcp local

_cansub._tcp                                    PTR     aabbccdd-usb._cansub._tcp
aabbccdd-usb._cansub._tcp                       TXT     "api=02.00" "channels=4"
```

### Linux

On Linux, the `avahi-browse`<sup>[4](#fn-avahi)</sup> tool can be used for mDNS discovery.

The `avahi-browse` tool used to detect a CANsub device with hostname `aabbccdd-usb`.

```console
$ avahi-browse _cansub._tcp --resolve

= enx0200aabbccdd IPv4 aabbccdd-usb     _cansub._tcp         local
hostname = [aabbccdd-usb.local]
address = [10.121.15.1]
port = [443]
txt = ["channels=4" "api=02.00"]
```

---

## Scanning

When mDNS discovery is not possible (e.g. when accessing the device via a VPN), the device can be found by scanning the subnet for services on port 443 (HTTPS).

#### NOTE
Scanning the network returns all devices with a service running on port 443 (HTTPS).

The `nmap`<sup>[5](#fn-nmap)</sup> tool can be used to scan the subnet to which the device is connected. In the example below, `192.168.1.0/24` covers the addresses 192.168.1.1 to 192.168.1.254.

Example of using `nmap` to scan the subnet `192.168.1.0/24` for services on port 443 (HTTPS).

```console
$ nmap -Pn -p 443 --open 192.168.1.0/24

Nmap scan report for 192.168.1.100
Host is up (0.00055s latency).
```

If `nmap` returns multiple results, confirm which belong to a CANsub device by probing the [REST API](https://canlogger.csselectronics.com/cansub-docs/cansub4/api/api_rest.html.md#device-info):

Example of using `curl` to verify the device ID.

```console
$ curl -k https://192.168.1.100/api/info

{"id":"aabbccdd","hw_ver":"01.02","fw_ver":"01.02.03","mac":"001122334455","usb":"04D8&E487"}
```

## Troubleshooting

If the device is not discovered, check the following possible causes:

- The PC and the device are not on the same network segment. mDNS multicast is not forwarded between networks, including VPN connections<sup>[6](#fn-vpn-ip)</sup> and virtual networks (e.g. WSL or Docker)<sup>[7](#fn-virtual-net)</sup>.
- A network device filters multicast packets between the PC and the device (e.g. a managed switch, Wi-Fi access point, or firewall).
- A firewall on the PC blocks mDNS packets (UDP port 5353). This is common when a USB network adapter is classified as a *Public network* on Windows.
- A VPN client is active on the PC and blocks or redirects mDNS packets on the local network.

---
* <a id='fn-mdns'>**[1]**</a> mDNS (Multicast DNS, RFC 6762) resolves hostnames on a local network without a DNS server.
* <a id='fn-dnssd'>**[2]**</a> DNS-SD (DNS Service Discovery, RFC 6763) advertises services on a local network.
* <a id='fn-dnssd-win'>**[3]**</a> `dns-sd.exe` is included with [Bonjour for Windows](https://support.apple.com/kb/DL999) (Apple).
* <a id='fn-avahi'>**[4]**</a> `avahi-browse` is part of the `avahi-utils` package.
* <a id='fn-nmap'>**[5]**</a> `nmap` is part of the `nmap` package on Linux. For Windows, an installer is available from [nmap.org](https://nmap.org/download.html).
* <a id='fn-vpn-ip'>**[6]**</a> The device can still be accessed via its IP address through a VPN connection, see [Scanning](#scanning).
* <a id='fn-virtual-net'>**[7]**</a> Virtual machines and containers can typically be configured to share the network of the host, which allows mDNS discovery from within the virtual environment.

[Security]:

# Security

Data transferred over the device network interface (USB or Ethernet) is secured by Transport Layer Security (TLS). TLS ensures that data exchanged with the CANsub.4 is encrypted and that the user is connecting to a genuine CANsub.4. When connected via Ethernet, access can optionally be restricted using [TLS Mutual Authentication](https://canlogger.csselectronics.com/cansub-docs/cansub4/connection/security/mtls.html.md#tls-mutual-authentication-mtls).

#### NOTE

# TLS Mutual Authentication (mTLS)

By default, TLS encrypts the connection but does not determine *who* is allowed to connect to the CANsub.4. TLS Mutual Authentication (mTLS) adds client verification, ensuring that only authenticated users can access the device, similar to password protection.

TLS Mutual Authentication uses asymmetric cryptography. Enabling it does not require storing any client secrets on the device. Only public certificate material is stored.

The CANsub.4 supports optional mTLS **over the Ethernet connection**<sup>[1](#fn-mtls-persistent)</sup>.

#### NOTE
The USB connection can always be used to regain access to the device (mTLS is never enforced over USB), for example if the client certificate or key is lost.

```bash
#!/bin/bash
set -euo pipefail

# Minimum steps to create a self-signed client certificate + key for mTLS.
# Usage: ./demo_cansub_self_signed_cert.sh [client_name] [password]

# Disable Git Bash (MSYS) path conversion on Windows (no effect on Linux/macOS).
export MSYS_NO_PATHCONV=1

CLIENT_NAME=${1:-client}
CLIENT_PASSWORD=${2:-}

CLIENT_KEY="${CLIENT_NAME}.key"
CLIENT_CRT="${CLIENT_NAME}.crt"
CLIENT_P12="${CLIENT_NAME}.p12"

# 1. Generate a private key (EC P-256, supported by the CANsub)
openssl genpkey -algorithm EC -pkeyopt ec_paramgen_curve:prime256v1 -out "${CLIENT_KEY}"
chmod 600 "${CLIENT_KEY}"

# 2. Generate a self-signed client certificate.
#    The extensions below make it a valid TLS client certificate:
#      basicConstraints=CA:FALSE     end-entity certificate, not a CA
#      keyUsage=digitalSignature     lets the client sign during the TLS handshake
#      extendedKeyUsage=clientAuth   marks the certificate for client authentication
openssl req -x509 -new -sha256 -key "${CLIENT_KEY}" -out "${CLIENT_CRT}" -days 3650 \
    -subj "/CN=${CLIENT_NAME}" \
    -addext "basicConstraints=critical,CA:FALSE" \
    -addext "keyUsage=critical,digitalSignature" \
    -addext "extendedKeyUsage=clientAuth"

# 3. Create a PKCS#12 bundle for browsers.
openssl pkcs12 -export -out "${CLIENT_P12}" \
    -inkey "${CLIENT_KEY}" \
    -in "${CLIENT_CRT}" \
    -name "${CLIENT_NAME}" \
    -passout "pass:${CLIENT_PASSWORD}"

if [ -z "${CLIENT_PASSWORD}" ]; then
    echo "Generated: ${CLIENT_KEY}, ${CLIENT_CRT}, ${CLIENT_P12} (no password)"
else
    echo "Generated: ${CLIENT_KEY}, ${CLIENT_CRT}, ${CLIENT_P12} (with password)"
fi
```

### CA-signed certificate

A certificate authority (CA) signs client certificates. Uploading the CA certificate (`ca.crt`) to the CANsub.4 makes the CANsub.4 trust every client certificate the CA signs. New clients can then be added without changing the CANsub.4 configuration, and the same CA certificate can be uploaded to multiple CANsub devices.

```mermaid
flowchart TB
    CAC["CA certificate<br>(ca.crt / ca.key)"]
    CAC -->|"signs" | A1["Client 1"]
    CAC -->|"signs" | A2["Client 2"]
    CAC -->|"signs" | A3["Client N"]
```

#### NOTE
When using a CA-signed certificate, upload `ca.crt` in [step 2](#upload-the-client-certificate) (rather than an individual client certificate). The CANsub.4 then trusts every client the CA signs.

The script<sup>[3](#fn-script-is-doc)</sup> below uses OpenSSL to create the CA and sign client certificates. Download, inspect, and run it once per client. The CA is created on the first run and reused for every client added afterwards:

[`demo_cansub_ca_signed_cert.sh`](https://canlogger.csselectronics.com/cansub-docs/cansub4/_downloads/4a461c9d668dd8b04ee3d8590afc2a0e/demo_cansub_ca_signed_cert.sh)
<br/>


The script generates the following files:

| File                | Sensitive   | Purpose                                                        |
|---------------------|-------------|----------------------------------------------------------------|
| `ca.crt`            | No          | CA public certificate. Uploaded to the CANsub.4.               |
| `ca.key`            | Yes         | CA private key. Signs client certificates.                     |
| `[CLIENT-NAME].crt` | No          | Client public certificate. Signed by the CA.                   |

| `[CLIENT-NAME].p12` | Yes         | Client `crt` and `key` bundled in one file for browser import. |
<details>
<summary>Show demo_cansub_ca_signed_cert.sh</summary>
```bash
#!/bin/bash
set -euo pipefail

# Minimum steps to create a CA-signed client certificate + key for mTLS.
# Usage: ./demo_cansub_ca_signed_cert.sh [client_name] [password]
# Re-run with a different client_name to enroll more users (the CA is reused).

# Disable Git Bash (MSYS) path conversion on Windows (no effect on Linux/macOS).
export MSYS_NO_PATHCONV=1

CLIENT_NAME=${1:-client}
CLIENT_PASSWORD=${2:-}

CLIENT_KEY="${CLIENT_NAME}.key"
CLIENT_CRT="${CLIENT_NAME}.crt"
CLIENT_P12="${CLIENT_NAME}.p12"
CLIENT_CSR="${CLIENT_NAME}.csr"

CA_NAME="CANsub Client CA"
CA_KEY="ca.key"
CA_CRT="ca.crt"
CA_CREATED=false

if [ ! -f "${CA_KEY}" ]; then

    # 1. Generate the root CA private key (EC P-256, supported by the CANsub).
    #    The CA key is reused to sign future client certificates.
    openssl genpkey -algorithm EC -pkeyopt ec_paramgen_curve:prime256v1 -out "${CA_KEY}"
    chmod 600 "${CA_KEY}"

    # 2. Generate the self-signed root CA certificate.
    #    basicConstraints=CA:TRUE and keyUsage=keyCertSign let it sign client certificates.
    openssl req -x509 -new -sha256 -key "${CA_KEY}" -out "${CA_CRT}" -days 7300 \
        -subj "/CN=${CA_NAME}" \
        -addext "basicConstraints=critical,CA:TRUE" \
        -addext "keyUsage=critical,keyCertSign"

    CA_CREATED=true
fi

# 3. Generate a private key (EC P-256, supported by the CANsub)
openssl genpkey -algorithm EC -pkeyopt ec_paramgen_curve:prime256v1 -out "${CLIENT_KEY}"
chmod 600 "${CLIENT_KEY}"

# 4. Generate a certificate signing request (CSR) for the client.
#    The requested extensions make it a valid TLS client certificate:
#      basicConstraints=CA:FALSE     end-entity certificate, not a CA
#      keyUsage=digitalSignature     lets the client sign during the TLS handshake
#      extendedKeyUsage=clientAuth   marks the certificate for client authentication
openssl req -new -sha256 -key "${CLIENT_KEY}" -out "${CLIENT_CSR}" \
    -subj "/CN=${CLIENT_NAME}" \
    -addext "basicConstraints=critical,CA:FALSE" \
    -addext "keyUsage=critical,digitalSignature" \
    -addext "extendedKeyUsage=clientAuth"

# 5. Sign the CSR with the CA, copying the requested extensions into the certificate.
openssl x509 -req -sha256 -in "${CLIENT_CSR}" -out "${CLIENT_CRT}" -days 3650 \
    -CA "${CA_CRT}" -CAkey "${CA_KEY}" \
    -copy_extensions copy

# Remove the intermediate CSR.
rm -f "${CLIENT_CSR}"

# 6. Create a PKCS#12 bundle for browsers.
openssl pkcs12 -export -out "${CLIENT_P12}" \
    -inkey "${CLIENT_KEY}" \
    -in "${CLIENT_CRT}" \
    -name "${CLIENT_NAME}" \
    -passout "pass:${CLIENT_PASSWORD}"

# Report the generated files, distinguishing a newly created CA from a reused one.
if [ "${CA_CREATED}" = true ]; then
    echo "Created CA: ${CA_CRT}, ${CA_KEY}"
else
    echo "Reused existing CA: ${CA_CRT}, ${CA_KEY}"
fi

if [ -z "${CLIENT_PASSWORD}" ]; then
    echo "Generated client files: ${CLIENT_KEY}, ${CLIENT_CRT}, ${CLIENT_P12} (no password)"
else
    echo "Generated client files: ${CLIENT_KEY}, ${CLIENT_CRT}, ${CLIENT_P12} (with password)"
fi
```

</details>

# Time

Accurate time is important for correlating frames across buses, across devices, and with data from other sources. The CANsub.4 maintains its own clock and uses it to timestamp every CAN bus frame (received or transmitted) with a resolution of 1 us (microsecond). The timestamp is applied by the device in hardware and is unaffected by the delay and jitter from the device to the connected client. The same clock is used to achieve accurate transmission scheduling.

The clock is reset on power-up and must be set. Like any clock, it also drifts, so a clock that was set accurately will slowly diverge from true time and from the clocks of other devices. The clock can be set manually through the REST API, or kept synchronized continuously using Precision Time Protocol (PTP). This section covers how frames are timestamped and both ways of setting the time.

> ##### Time topics
> 
> * [Timestamping](#timestamping)
> * [Manual time setting (REST)](#manual-time-setting-rest)
> * [Automatic time synchronization (PTP)](#automatic-time-synchronization-ptp)

---

## Timestamping

The CANsub.4 timestamps both received and transmitted CAN bus frames in hardware on the start-of-frame (SOF) bit, with a resolution of 1 us. All CAN buses on the device share the same clock, so timestamps from different buses can be compared directly. Received and transmitted frames can likewise be compared directly, since both are timestamped at the same bit, as illustrated below.

![Frames are timestamped at the start-of-frame (SOF) bit, in both directions.](time/timestamp_sof.png)

#### NOTE
A transmitted frame is timestamped when it actually goes on the bus, after any queued frames and arbitration. The device reports this time to the client in a transmission acknowledgement frame over the [WebSocket](https://canlogger.csselectronics.com/cansub-docs/cansub4/api/api_ws.html.md#can-frame) (if enabled for the channel).

The table below gives the approximate time a classical CAN frame occupies the bus, including the interframe space and typical stuff bits.

| Frame                   | Bit rate   | Bits   | Time on bus   |
|-------------------------|------------|--------|---------------|
| 11-bit ID, 8 data bytes | 250 kbit/s | ~120   | ~0.5 ms       |
| 11-bit ID, 0 data bytes | 1 Mbit/s   | ~50    | ~50 us        |

A resolution of 1 us is sufficient for CAN bus frames. Even the shortest frame at the highest classical bit rate occupies the bus for tens of microseconds, so consecutive frames on a bus always get distinct timestamps and their order and spacing are preserved.

A resolution of 1 ms is not sufficient. At 1 Mbit/s, around 20 short frames fit within 1 ms and could receive the same timestamp.

---

## Manual time setting (REST)

The device time can be set via the [REST API](https://canlogger.csselectronics.com/cansub-docs/cansub4/api/api_rest.html.md#device-time). This method is sufficient to ensure that frames from the same device always get distinct timestamps and their order and spacing are preserved.

Setting the time via the REST API has the following limitations:

- The network delay adds an unknown offset between the client clock and the device clock.
- The client clock and the device clock drift apart over time.

These limitations can become an issue when comparing data between multiple CANsub devices, or with data from another source. The figure below shows a practical test where two CANsub devices, both set via REST, receive the same CAN bus frames.

![The same CAN bus signal timestamped by two CANsub devices. The horizontal shift shows a relative time error of ~1 ms. The error depends on the network and on the time since the clocks were set, and can become considerably larger.](time/time_rest.png)

The same REST endpoint also accepts a clock rate correction. A client that measures how the device clock drifts relative to its own clock can apply this correction to reduce the drift. This allows a rough client-controlled steering of the device clock when [PTP synchronization](#automatic-time-synchronization-ptp) is not an option.

#### NOTE
Setting the time manually overrides and disables [PTP synchronization](#automatic-time-synchronization-ptp) for the rest of the power cycle.

---

## Automatic time synchronization (PTP)

The device time can be kept synchronized continuously using PTP. Synchronization is enabled by default and starts automatically when a compatible PTP master (network time source) is detected.

See [Precision Time Protocol (PTP)](https://canlogger.csselectronics.com/cansub-docs/cansub4/time/ptp/index.html.md#precision-time-protocol-ptp) for more details on the supported master configuration and the measured performance of a range of deployments.

PTP removes the limitations of setting the time manually:

- The network delay is continuously measured and compensated for.
- The device clock rate is continuously adjusted to track the master clock.

CANsub devices (and external data sources) synchronized to the same PTP master share a common time, and data can be compared directly. The figure below repeats the test from the previous section, with both devices synchronized via PTP.

![The same CAN bus signal timestamped by two CANsub devices synchronized via PTP, using a dedicated PTP master (TM2000B). The relative error approaches the timestamp resolution.](time/time_ptp.png)

# Precision Time Protocol (PTP)

Precision Time Protocol (PTP, IEEE 1588) is used for synchronizing clocks on a local network. PTP can reach sub-microsecond accuracy, while Network Time Protocol (NTP) typically achieves millisecond accuracy. The achievable accuracy depends on how well the network, the master and the clients meet the assumptions PTP relies on, see [Performance](#performance).

A PTP *master* provides the time to one or more PTP *clients*. The master can be a dedicated hardware device or a PC running PTP software.

The CANsub.4 acts as a PTP client and synchronizes by default to a PTP master via either Ethernet or USB. The device selects the first compatible master it detects<sup>[1](#fn-first-master)</sup> and then continuously tracks its time. Time errors above 100 ms are corrected by stepping the clock, smaller errors by adjusting the clock rate. The state of the synchronization can be read via the [REST API](https://canlogger.csselectronics.com/cansub-docs/cansub4/api/api_rest.html.md#device-time-ptp-status) and is shown on the [display](https://canlogger.csselectronics.com/cansub-docs/cansub4/hardware/display.html.md#display) while tracking.

#### NOTE
Setting the time manually via the REST API overrides and disables PTP synchronization for the rest of the power cycle. A power cycle or reboot re-enables it.

> ##### PTP topics
> 
> * [Supported master configuration](#supported-master-configuration)
> * [Performance](#performance)
> * [Troubleshooting](#troubleshooting)

## Supported master configuration

#### Supported PTP master configuration. Recommended in bold.

| Configuration                                         | Supported                                            |
|-------------------------------------------------------|------------------------------------------------------|
| Version                                               | 2.0 or **2.1**                                       |
| Profile                                               | Default IEEE 1588 (`majorSdoId` 0)                   |
| Transport                                             | IPv4 UDP                                             |
| Addressing                                            | Multicast only (224.0.1.129, port 319/320)           |
| Delay mechanism                                       | End-to-End (E2E)                                     |
| Step mode                                             | **One-step**<sup>[2](#fn-one-step)</sup> or two-step |
| Announce interval                                     | Any (**1 (2 s)** recommended)                        |
| Sync interval (`logSyncInterval`)                     | -1 (500 ms), **0 (1 s)**, 1 (2 s)                    |
| Min delay request interval (`logMinDelayReqInterval`) | At or below `logSyncInterval`                        |
| Timescale                                             | TAI or UTC                                           |
| UTC offset                                            | TAI: 37 required, UTC: ignored                       |
| Domain number                                         | 0                                                    |
| TLVs                                                  | A message carrying a TLV is discarded                |

#### NOTE
PTP over IPv4 UDP uses port 319 for event messages and port 320 for general messages. A PC running the PTP master must allow UDP traffic on both ports in both directions.

## Performance

The CANsub.4 detects a PTP master within one Announce interval (typically 2 s) and starts tracking within 10 to 20 s (with a Sync interval of 1 s). The PTP state can be read via the [REST API](https://canlogger.csselectronics.com/cansub-docs/cansub4/api/api_rest.html.md#device-time-ptp-status)<sup>[5](#fn-ptp-status-browser)</sup>.

The achievable time synchronization accuracy depends on how well the following PTP assumptions hold:

1. Network packets are accurately timestamped
2. Network delay is symmetric (the same in both directions)
3. Network delay does not change significantly between packets

The examples below demonstrate the achievable time synchronization accuracy in various scenarios. For each, the relative accuracy is evaluated by comparing the timestamps of two CANsub devices connected to the same CAN bus (one transmits, one receives).

### Dedicated hardware

A dedicated PTP master is able to timestamp network packets accurately (assumption 1) and can typically provide high absolute time accuracy based on an external source (such as GPS).

An example network with a dedicated PTP master is illustrated below.

```mermaid
flowchart LR
    GPS(["External time source<br>(e.g. GPS)"])
    GPS --> M["PTP master<br>(hardware timestamping)"]
    M --- SW["Ethernet switch"]
    SW --- D1["CANsub 1"]
    SW --- D2["CANsub 2"]
    SW --- DN["CANsub N"]
```

PTP over Ethernet. Dedicated master with hardware timestamping, synchronized to GPS.

Measurements show that the relative error (between two devices) approaches the timestamp resolution of 1 us.

![Relative timestamp error between two CANsub devices before (red) and after (green) PTP tracking. Dedicated master (TM2000B) over Ethernet.](time/ptp/ptp_performance/ptp_eth_hw.png)

### Software using ptp4l

A PC running a PTP master software tool typically timestamps network packets less accurately than a dedicated master and uses a less accurate external time source (such as NTP).

An example network with a Linux PC running the PTP for Linux (`ptp4l`) software tool<sup>[3](#fn-ptp4l-linux)</sup> is illustrated below.

```mermaid
flowchart LR
    NTP(["External time source<br>(NTP)"])
    NTP --> M["PC running ptp4l<br>(software timestamping)"]
    M --- SW["Ethernet switch /<br>USB hub"]
    SW --- D1["CANsub 1"]
    SW --- D2["CANsub 2"]
    SW --- DN["CANsub N"]
```

PTP over Ethernet or USB. `ptp4l` master with software timestamping, synchronized to NTP.

Measurements show that the relative error (between two devices) stays within tens of microseconds via both Ethernet and USB.

![Relative timestamp error between two CANsub devices before (red) and after (green) PTP tracking. ptp4l master over Ethernet.](time/ptp/ptp_performance/ptp_eth_sw.png)![Relative timestamp error between two CANsub devices before (red) and after (green) PTP tracking. ptp4l master over USB.](time/ptp/ptp_performance/ptp_usb_sw.png)

The `ptp4l` tool (package name `linuxptp`) can be started as in the following examples:

Example: ptp4l master on one Ethernet interface.

```bash
sudo ptp4l -S -4 -m -i eth1
```

Example: ptp4l master on two USB interfaces (a USB interface only exists while the device is plugged in).

```bash
sudo ptp4l -S -4 -m -i enx0200aabbccdd -i enx0200aabbccee
```

#### NOTE
See [Discovery](https://canlogger.csselectronics.com/cansub-docs/cansub4/connection/discovery.html.md#discovery) for information on how to find device and network interface names.

#### NOTE
Firewalls commonly block PTP traffic by default. UDP ports 319 and 320 must be open in both directions.

## Troubleshooting

The [PTP status endpoint](https://canlogger.csselectronics.com/cansub-docs/cansub4/api/api_rest.html.md#device-time-ptp-status)<sup>[5](#fn-ptp-status-browser)</sup> is useful for troubleshooting.

**Master is not found**

- The master Announce message is incompatible, see [Supported master configuration](#supported-master-configuration).
- The master Announce message is blocked from reaching the device (UDP port 320).
- The master and the device are not on the same network segment. PTP multicast is not forwarded between networks, including virtual networks (e.g. WSL or Docker)<sup>[4](#fn-virtual-net)</sup>.
- A network device filters multicast packets between the master and the device (e.g. a managed switch or firewall).

**Master is found but the device is not tracking**

- The master Sync message is incompatible, see [Supported master configuration](#supported-master-configuration).
- The master Sync message (UDP port 319) or Delay Response message (UDP port 320) is blocked from reaching the device.
- The device Delay Request message is blocked from reaching the master (UDP port 319).
- The master clock rate differs from the device clock rate by more than 200 ppm.
- The master was replaced after the device selected it. The device keeps the first master for the rest of the power cycle, so reboot the device after moving the master to another PC, interface, or hardware unit.

**Tracking is lost**

- The master Sync message has stopped.
- The master clock has jumped by more than 100 ms (the device resynchronizes).

**PTP is disabled**

- The device time was set manually, disabling PTP for the rest of the power cycle. Reboot the device.

---
* <a id='fn-first-master'>**[1]**</a> The selected master is kept for the rest of the power cycle.
* <a id='fn-one-step'>**[2]**</a> One-step requires hardware timestamping support in the master. Software masters use two-step.
* <a id='fn-ptp4l-linux'>**[3]**</a> `ptp4l` is available for Linux only. No equivalent PTP master software is known for Windows.
* <a id='fn-virtual-net'>**[4]**</a> Virtual machines and containers can typically be configured to share the network of the host, which allows PTP multicast to reach the device.
* <a id='fn-ptp-status-browser'>**[5]**</a> The PTP status endpoint can be opened directly in a browser, e.g. `https://aabbccdd-eth.local/api/time/ptp` or `https://aabbccdd-usb.local/api/time/ptp`.

## Usage

A typical integration follows this flow:

```mermaid
flowchart LR
init["1. Initialize"] --> configure
subgraph channels ["For each channel"]
    configure["2. Configure channel"] --> open["3. Open channel"]
    open --> service["4. Communicate"]
    service --> close["5. Close channel"]
end
```

1. **Initialize**  *(once)*: Verify the API version and set the device time if needed (REST)
2. **Configure channel**  *(per channel)*: Configure the CAN channel (REST)
3. **Open channel**: Connect the WebSocket to open the CAN channel (WebSocket)<sup>[2](#fn-websocket-client)</sup>
4. **Communicate**: Communicate with the CAN bus (WebSocket) and monitor states (REST)
5. **Close channel**: Disconnect the WebSocket to close the CAN channel (WebSocket)

For more details, see [REST API](https://canlogger.csselectronics.com/cansub-docs/cansub4/api/api_rest.html.md#rest-api) and [WebSocket API](https://canlogger.csselectronics.com/cansub-docs/cansub4/api/api_ws.html.md#websocket-api). See [Closing the connection](https://canlogger.csselectronics.com/cansub-docs/cansub4/api/api_ws.html.md#closing-the-connection) for the recommended close sequence.

## Device time

Read (GET) or set (PUT) the device time (wall-clock time) and the clock rate correction. The device time needs to be set for the device to be able to correctly timestamp CAN bus frames, see [Time](https://canlogger.csselectronics.com/cansub-docs/cansub4/time/index.html.md#time).

The rate correction adjusts how fast the device clock runs, in parts per billion. It allows a client with a known estimate of the device clock error to compensate for drift. Use `0` when no correction is known.

#### NOTE
The time is reset on power cycles and is shared across all CAN channels.

#### NOTE
Setting the time overrides and disables [PTP synchronization](https://canlogger.csselectronics.com/cansub-docs/cansub4/time/index.html.md#automatic-time-synchronization-ptp) for the rest of the power cycle.

### GET /api/time

**Get device time**

Returns the current device time and the clock rate correction currently applied.

**Example request:**

```http
GET /api/time HTTP/1.1
Host: example.com
```

* **Status Codes:**
  * [200 OK](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Status/200) – 

    Current device time and rate correction.

    **Example response:**
    ```http
    HTTP/1.1 200 OK
    Content-Type: application/json

    {
        "utc": "2025-01-01T00:00:00.000Z",
        "rate_ppb": 0
    }
    ```

### PUT /api/time

**Set device time**

Sets the device time and the clock rate correction. Overrides and disables time synchronization for the rest of the power cycle.

**Example request:**

```http
PUT /api/time HTTP/1.1
Host: example.com
Content-Type: application/json

{
    "utc": "2025-01-01T00:00:00.000Z",
    "rate_ppb": 0
}
```

* **Status Codes:**
  * [200 OK](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Status/200) – Device time set successfully.
  * [400 Bad Request](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Status/400) – Bad request (invalid object, unsupported time format, or time or rate outside the supported range).

The time value (GET response and PUT request body) has the following format.

| type           | *object*                                                                                                                                                                                      |
|----------------|-----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| properties     |                                                                                                                                                                                               |
| - **utc**      | Device time as an RFC3339/ISO-8601 UTC timestamp string, format YYYY-MM-DDTHH:MM:SS.sssZ. Must be 2025-01-01T00:00:00.000Z or later.                                                          |
| type           | *string*                                                                                                                                                                                      |
| format         | date-time                                                                                                                                                                                     |

Abort (DELETE) the WebSocket connection of a specific CAN channel. See [Closing the connection](https://canlogger.csselectronics.com/cansub-docs/cansub4/api/api_ws.html.md#closing-the-connection) for the recommended close sequence.

### DELETE /api/can/{channel}/ws

**Abort CAN channel WebSocket connection**

Aborts the channel WebSocket connection. Queued data is discarded (not transmitted on the CAN bus), allowing the connection to close even when the bus cannot transmit the queued data.

* **Parameters:**
  * **channel** (*integer*)
* **Status Codes:**
  * [200 OK](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Status/200) – WebSocket connection abort requested.
  * [404 Not Found](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Status/404) – No active WebSocket connection on the channel.

#### NOTE
CAN bus frames are transferred via the WebSocket connection itself, see the [WebSocket API](https://canlogger.csselectronics.com/cansub-docs/cansub4/api/api_ws.html.md#websocket-api).

# WebSocket API

The WebSocket API is used to transfer CAN bus frames between the connected client and the CANsub.4.

This page uses the term *frame* in three distinct contexts:

- **CAN frame**: A CAN bus frame.
- **HDLC frame**: A delimited binary container for boundary detection and integrity verification.
- **Network frame**: A network-layer data frame.

#### NOTE
Device configuration and state monitoring are done via the [REST API](https://canlogger.csselectronics.com/cansub-docs/cansub4/api/api_rest.html.md#rest-api).

---

## WebSocket usage

The `/api/can/{channel}/ws` endpoints (one for each physical channel) accept WebSocket upgrades. Only one client can be connected to each WebSocket at a time. Live data is transferred using WebSocket **binary messages**. The format of the binary data is described below.

**Connecting a WebSocket opens the associated CAN bus (channel) on the device. Disconnecting closes the channel** (see [Closing the connection](#closing-the-connection)).

The connection is bidirectional:

- **CANsub → Client**: the CANsub sends received CAN frames, CAN transmission acknowledgements, and CAN error frames.
- **Client → CANsub**: the client sends CAN frames to be transmitted on a physical CAN bus.

### Receive

Receiving data from the WebSocket is illustrated (simplified) below. Reception follows these steps (explained in more detail below):

1. Read bytes from the WebSocket until a start and an end boundary byte are found.
2. Perform byte destuffing and remove boundary bytes.
3. Validate CRC32.
4. Deserialize CAN frames until no bytes remain (a payload can contain one or more CAN frames).

```mermaid
flowchart LR
    ws[Read WebSocket] -->|"0x7E...0x7E" | destuf["Destuff"]
    destuf -->|"CRC OK" | deserial["Deserialize"]
```

### Transmit

Transmitting data to the WebSocket is illustrated (simplified) below. Transmission follows these steps (explained in more detail below):

1. Serialize CAN frames (one or more).
2. Calculate CRC32.
3. Perform byte stuffing and add boundary bytes.
4. Write bytes to the WebSocket<sup>[1](#fn-websocket-max)</sup>.

```mermaid
flowchart LR
    serialize["Serialize"] --> crc["Calculate CRC32"] --> stuf["Stuff"] --> ws["Write WebSocket"]
```

---

## Closing the connection

A WebSocket connection is closed by sending a WebSocket close message to the CANsub.4. When the CANsub.4 receives the WebSocket close message, it performs the following steps:

1. Completes queued CAN frame transmissions (without a timeout)
2. Closes the CAN bus
3. Confirms the WebSocket close message

The client can abort step 1 by sending a [DELETE request](https://canlogger.csselectronics.com/cansub-docs/cansub4/api/api_rest.html.md#can-channel-websocket) to the WebSocket endpoint `/api/can/{channel}/ws`. The CANsub.4 then discards the queued CAN frames and completes the close immediately. The DELETE request can be used as a client-controlled timeout for step 1.

```mermaid
flowchart LR
    subgraph queue["TCP queue"]
        direction LR
        close["WS close"] --> canb["CAN frame"] --> cana["CAN frame"]
    end
    dev["Device"]
    cana --> dev

    style cana fill:#FF9900,stroke:#FFFFFF
    style canb fill:#FF9900,stroke:#FFFFFF
```

A `DELETE` request discards the queued CAN frames (orange), such that the CANsub.4 reads the WebSocket close frame immediately.

### Recommended close sequence

1. Send a WebSocket close message.
2. Await close confirmation.
3. If no confirmation arrives within a (client-controlled) timeout period, issue a DELETE request and await the confirmation, which should now arrive immediately.

#### NOTE
Use the WebSocket close handshake when closing the connection. Avoid closing the TCP connection directly.

## HDLC frame

Each HDLC frame carries one or more serialized CAN frames. HDLC framing provides boundary detection, payload integrity verification, and byte-stuffing.

#### HDLC frame structure.

| Boundary byte   | Payload           | CRC32   | Boundary byte   |
|-----------------|-------------------|---------|-----------------|
| `0x7E`          | N bytes (stuffed) | 4 B     | `0x7E`          |
- `0x7E` marks the start and end of each HDLC frame.
- *payload*: one or more serialized CAN frames concatenated (see [CAN frame]()).
- *CRC32*: IEEE 802.3 CRC32 (polynomial `0xEDB88320`) computed over the raw (unstuffed) payload bytes, appended in big-endian byte order.
- Byte-stuffing is applied to all bytes between the boundary bytes (payload + CRC32 bytes).

### Byte-stuffing

Byte-stuffing ensures that the boundary byte (`0x7E`) does not appear in the HDLC frame body. Before transmission, every payload and CRC32 byte is stuffed.

#### Byte-stuffing substitutions.

| Original   | Encoded sequence   |
|------------|--------------------|
| `0x7E`     | `0x7D` `0x5E`      |
| `0x7D`     | `0x7D` `0x5D`      |

The escape byte `0x7D` is always followed by the original byte XOR `0x20`. On decoding, each `0x7D` causes the next byte to be XOR-ed with `0x20` to recover the original value.

## CAN frame

CAN bus frames are serialized as specified below.

#### `CB`: Classical-Base, `CE`: Classical-Extended, `FB`: FD-Base, `FE`: FD-Extended, `ER`: Error.

|     |           |        |     |     |     |     |        |    |    |    |    |    |    |   Byte |   0-5 |   6 |   7 | 8   | 9   | 10   |
|-----|-----------|--------|-----|-----|-----|-----|--------|----|----|----|----|----|----|--------|-------|-----|-----|-----|-----|------|
| Bit | 47-0      | 7      | 6   | 5   | 4   | 3   | 2      |  1 |  0 | 7  |  6 | 5  | 4  |      3 |     2 |   1 |   0 | 7-0 | 7-0 | 7-0  |
| CB  | TIMESTAMP | FDF(0) | RTR | 0   | TX  | DLC | IDE(0) |  0 |  0 | 0  |  0 | ID | -  |        |       |     |     |     |     |      |
| CE  | TIMESTAMP | FDF(0) | RTR | 0   | TX  | DLC | IDE(1) |  0 |  0 | ID |    |    |    |        |       |     |     |     |     |      |
| FB  | TIMESTAMP | FDF(1) | BRS | ESI | TX  | DLC | IDE(0) |  0 |  0 | 0  |  0 | ID | -  |        |       |     |     |     |     |      |
| FE  | TIMESTAMP | FDF(1) | BRS | ESI | TX  | DLC | IDE(1) |  0 |  0 | ID |    |    |    |        |       |     |     |     |     |      |
| ER  | TIMESTAMP | 0      | 0   | 1   | ERR | -   |        |    |    |    |    |    |    |        |       |     |     |     |     |      |
- `TIMESTAMP`: Timestamp in microseconds since 2025-01-01 00:00:00 UTC (offset: 1735689600000000 us)
- `FDF`: FD Format Indicator
- `RTR`: Remote Transmission Request
- `BRS`: Bit Rate Switch
- `ESI`: Error State Indicator
- `TX`: Transmission Acknowledgement
- `DLC`: Data Length Code
- `IDE`: Identifier Extension
- `ID`:  Identifier
- `ERR`: Error type
  > - `0`: Bit (bit 0 or bit 1)
  > - `1`: Ack
  > - `2`: Form
  > - `3`: Stuff
  > - `4`: CRC

# Firmware

The firmware of the CANsub.4 can be updated directly from a browser.

#### WARNING
A firmware update clears persistent device data (such as a configured mTLS certificate).

---

## Firmware update steps

1. Download and unzip the new firmware (see firmware files below).
2. Connect the CANsub.4 to a PC using a USB-C cable<sup>[1](#fn-update-via-ethernet)</sup>.
3. Open the firmware update page in a browser<sup>[2](#fn-url)</sup>:
   ```text
   https://[DEVICE-ID]-usb.local/firmware
   ```
4. Follow the steps on the page to update the firmware.

```markdown
### Warning

- WebSocket queue discard via DELETE /api/can/{channel}/ws, see documentation for details

- WebSocket graceful shutdown procedure changed, see documentation for details

### Warning
```

## Versioning & naming

The firmware version follows semantic versioning (`MAJOR.MINOR.PATCH`).

* `MAJOR`: Breaking changes
* `MINOR`: Backward-compatible changes
* `PATCH`: Backward-compatible fixes

# Install client certificate (mTLS)

When mTLS is enabled, the CANsub.4 only grants access to a browser that presents a valid client certificate and key. The [Enable Mutual Authentication](https://canlogger.csselectronics.com/cansub-docs/cansub4/connection/security/mtls.html.md#enable-mutual-authentication) guide bundles the client certificate and key into a single PKCS#12 file (`[CLIENT-NAME].p12`) for this purpose.

This page covers importing that bundle into Chrome and Firefox. OS-level installation is outside the scope of this manual.

> ##### Client certificate installation guides
> 
> * [Chrome browser](#chrome-browser)
> * [Firefox browser](#firefox-browser)

#### NOTE
Steps may differ slightly depending on OS and browser version.

---

## Chrome browser

1. Enter the following URL in the Chrome address bar to open the Certificate Manager.
   ```text
   chrome://certificate-manager/
   ```

   ![image](getting_started/certificate/chrome_1.png)
2. Click *Your certificates*, then *Manage imported certificates from …* or *View imported certificates from …* (depending on OS and version).
   ![image](connection/security/client_certificate/chrome_2.png)
3. Click *Import*.
   ![image](connection/security/client_certificate/chrome_3.png)
4. Navigate to the client certificate bundle file (`.p12`) and click *Select*. Ensure the file extension filter includes `.p12`.
   ![image](connection/security/client_certificate/chrome_4.png)
5. Enter the *certificate password* chosen when the `.p12` file was created (leave blank if no password was set).
   ![image](connection/security/client_certificate/chrome_5.png)
6. The certificate is now listed under *Your certificates*.
   ![image](connection/security/client_certificate/chrome_6.png)
7. When accessing the CANsub.4 over the Ethernet connection, the browser prompts for a client certificate. Select the installed certificate and click *OK*.
   ![image](connection/security/client_certificate/chrome_7.png)

   ![image](getting_started/certificate/firefox_2.png)

   ![image](connection/security/client_certificate/firefox_3.png)
4. Navigate to the client certificate bundle file (`.p12`) and click *Select*.
   ![image](connection/security/client_certificate/firefox_4.png)
5. Enter the *certificate password* chosen when the `.p12` file was created (leave blank if no password was set).
   ![image](connection/security/client_certificate/firefox_5.png)
6. The certificate is now listed under *Your Certificates*.
   ![image](connection/security/client_certificate/firefox_6.png)
7. When accessing the CANsub.4 over the Ethernet connection, the browser prompts for a client certificate. Select the installed certificate and click *OK*.
   ![image](connection/security/client_certificate/firefox_7.png)

[TLS handshake]:

# TLS handshake

The sequence diagram below provides a simplified overview of the TLS handshake between the client and the CANsub.4, including the optional TLS Mutual Authentication sequence. It does not cover every detail of the TLS protocol.

```mermaid
sequenceDiagram
    participant Client as Client (user)
    participant Server as Server (CANsub)

    Client->>Server: ClientHello
    Note over Client,Server: Client proposes TLS version, cipher suites, and random value

    Server->>Client: ServerHello
    Note over Client,Server: Server selects TLS version and cipher suite,<br>and sends random value

    Server->>Client: Server certificate (public)
    Server->>Client: CertificateVerify (proving server owns private key)

    Client->>Client: Verify server identity

    opt Mutual Authentication only
        Server->>Client: CertificateRequest
        Client->>Server: Client certificate (public)
        Client->>Server: CertificateVerify (proving client owns private key)

        Server->>Server: Verify client identity
    end

    Client->>Server: Complete TLS handshake
    Server->>Client: Complete TLS handshake

    Note over Client,Server: Encrypted TLS connection established

    Client<<->>Server: Encrypted application data
```

# CANsub certificate installation

Installing the CANsub root certificate allows the browser to trust the CANsub.4 without displaying a security warning.

The guides below cover installation of the certificate in the Chrome and Firefox browsers. OS-level installation is outside the scope of this manual. Steps may differ slightly depending on the browser version.

> * [Firefox browser](#firefox-browser)

   ```text
   chrome://certificate-manager/
   ```

   ![image](getting_started/certificate/chrome_1.png)

   ![image](getting_started/certificate/chrome_2.png)

   ![image](getting_started/certificate/chrome_3.png)

   ![image](getting_started/certificate/chrome_4.png)

   ![image](getting_started/certificate/chrome_5.png)

## Firefox browser

1. Enter the following URL in the Firefox address bar to open Privacy & Security settings.
   ```text
   about:preferences#privacy
   ```

   ![image](getting_started/certificate/firefox_1.png)

   ![image](getting_started/certificate/firefox_2.png)

   ![image](getting_started/certificate/firefox_3.png)
